# Production Audit — ev-charging-stations-api

Audited: 2026-10-15
Method: running server + headless Chrome (CDP) against the real playground, plus a
direct probe of all 39 endpoint/edge-case combinations. Every finding below was
reproduced, not inferred.

---

## A. The biggest problem: the API is not actually deployed

`https://ev-charging-stations-api.vercel.app` returns **404** on `/`, `/health` and
every other path.

```
$ curl -o /dev/null -w "%{http_code}" https://ev-charging-stations-api.vercel.app/
404
$ curl -o /dev/null -w "%{http_code}" https://ev-charging-stations-api.vercel.app/health
404
```

Meanwhile the domain is baked into:

- all four README badges and both README "Base URL" lines
- `frontend/index.html` `<link rel="canonical">`, `og:url`
- `frontend/scripts/prerender.mjs` (`robots.txt` Sitemap line, all 8 `sitemap.xml`
  entries, every prerendered canonical tag)
- every `curl` example on the home page and in the docs

So the repository ships crawler directives pointing at a dead host. `STATUS.md`
correctly lists "Deploy to Vercel via CLI" as *next up*, but `README.md` and
`api.json` present the service as live. Nothing can be called production-grade
until this is resolved — either deploy, or stop advertising the URL as live.

## B. Backend / API defects

### B1. Rate limiting is global, not per client (critical)

`backend/src/app.js` never sets `trust proxy`. Behind Vercel's edge the Express
`req.ip` is the proxy, so **every user on the internet shares one 100-request /
15-minute bucket**. The API 429s globally after 100 requests.

Reproduced — two different client IPs, same bucket:

```
$ curl -D- -o /dev/null -H "X-Forwarded-For: 203.0.113.9" localhost:3000/v1/stations?limit=1
RateLimit-Remaining: 0
$ curl -D- -o /dev/null -H "X-Forwarded-For: 198.51.100.7" localhost:3000/v1/stations?limit=1
RateLimit-Remaining: 0
```

The 429 response itself is well-formed (standard `RateLimit-*` headers,
`Retry-After`, correct error envelope) — the keying is what is broken.

### B2. Malformed station IDs silently return the wrong station

`getStationById` uses `parseInt`, so anything with a numeric prefix resolves to
that number:

| Request | Result |
|---|---|
| `/v1/stations/1.5` | 200, returns station **1** |
| `/v1/stations/1e3` | 200, returns station **1** |

Should be `400 INVALID_STATION_ID`.

### B3. Numeric filters are silently ignored while reporting that they were applied

```
$ curl "localhost:3000/v1/stations?min_power_kw=abc"
meta.filters_applied.min_power_kw = "abc"     # but no filtering happened
filters_applied says a filter ran
```

`lat=abc` correctly returns 400, so the API is inconsistent with itself. A
developer filtering by `min_power_kw=100abc` gets the unfiltered dataset back
with metadata claiming it was filtered.

### B4. Query parameters are never trimmed

```
$ curl "localhost:3000/v1/stations?city=%20Mumbai%20"   → total: 0
```

Same for `state`, `operator`, `connector` — a stray space silently returns an
empty result set instead of matching or erroring.

### B5. `radius=0` and negative radii behave differently and silently

- `radius=0` → silently becomes **10 km** (`Number(0) || 10`)
- `radius=-5` → silently becomes **1 km**
- `radius=100` → capped, fine

Both are silent surprises. `radius=0` should be a 400.

### B6. Connector matching has no normalization

`connector=CCS-2` → 16,406 stations. `connector=CCS 2` → **0**. `connector=CCS2`
→ 0. Only the exact hyphenated spelling works, and it is documented nowhere.

### B7. No city aliasing

`city=Bengaluru` → 1,806. `city=Bangalore` → **0**. The dataset uses formal names
only, so the most common colloquial spellings return empty sets.

### B8. The dataset has 22 states, but the whole project claims 36

```
backend/data/states.json        → 22 entries
/v1/states  meta.count          → 22
backend/data/meta.json          → "total_states": 36   ← hardcoded, wrong
```

"36 States & UTs" appears in `README.md`, `HomePage.jsx` (3×), `DocsPage.jsx`,
`StatusPage.jsx`, and `STATUS.md`. India has 28 states + 8 UTs, but this snapshot
only covers 22 — the claim is unverified for this dataset and contradicts the
API's own response.

### B9. Documented parameters do not exist

`HomePage.jsx` advertises:

- `/v1/stations?state=Maharashtra&min_power=50` — the parameter is `min_power_kw`
- `Parameters: state, city, operator, min_power, limit, offset` — there is no
  `offset`; pagination is `page` + `limit`
- sample responses with `meta.query_time_ms`, `meta.lat`, `meta.lng`,
  `meta.returned`, `meta.offset` — **none of these fields exist**. The real
  `/v1/stations/near` meta is `{ center, radius_km, count, total_found }`

`README.md` has the same `min_power` error. Copy-pasting any of these examples
returns an unfiltered result set that looks like it worked.

### B10. The "< 4 ms" latency claim is not reproducible

Cold first request to `/v1/stations` measured **90 ms** (17.8 MB `require` of
`stations.json`). Warm requests are 1–15 ms. On Vercel serverless, every cold
start pays that cost. `STATUS.md`, `HomePage.jsx` ("AVG_SPATIAL_LATENCY < 3.8 ms")
and `StatusPage.jsx` ("Verified Value < 3.8 ms", "SLO Target") present a
fabricated benchmark as a measured one.

## C. Playground defects (the "not working properly" part)

### C1. Every keystroke fires an API request

```js
useEffect(() => { runQuery(); }, [lat, lng, radius]);
```

Latitude and longitude are free-text inputs wired straight into the effect, so
typing fans out one request per character. Reproduced — 6 keystrokes, 6 requests
in 1.3 s, three of them 400s:

```
200 /v1/stations/near?lat=0&lng=...
200 /v1/stations/near?lat=01&lng=...
200 /v1/stations/near?lat=012&lng=...
400 /v1/stations/near?lat=0123&lng=...
400 /v1/stations/near?lat=01234&lng=...
400 /v1/stations/near?lat=012345&lng=...
```

There is no debounce and no request cancellation, and `02`/`012` are treated as
valid latitudes. Combined with B1 this is how a user single-handedly exhausts the
shared quota.

### C2. `alert()` on geolocation failure freezes the page

Clicking **"LOCATE: USE CURRENT GPS COORDS"** with permission denied calls
`alert()`, which blocks the renderer. It hung the automation harness mid-run:

```
dialogs: [["alert","Location access denied or unavailable: User denied Geolocation"]]
```

Two problems: a raw internal message goes to the user, and a native blocking
dialog is used where inline feedback belongs. There is no retry and no fallback.

### C3. The connector filter produces false "no stations found"

The API returns only the nearest `limit` (25) results; the connector filter is
then applied **client side** to that already-truncated page. Verified:

```
filter = BHARAT DC →
  header:  "NEARBY_STATIONS (0)  TOTAL_IN_RADIUS: 0"
  emptyState: true
  markers: 0
```

The list and the map both empty out and tell the user there is nothing nearby,
even when hundreds of matching stations exist in the radius. Filtering has to
happen server-side via the `connector` parameter that already exists.

### C4. A failed query leaves misleading state on screen

After a 400 the error banner appears, but `meta` from the previous successful
response is still rendered — the header read `TOTAL_IN_RADIUS: 0` while the
banner reported an invalid-latitude error. Errors should clear or clearly mark
the results as stale.

### C5. The 429 is unrecoverable

Reproduced by hammering EXECUTE:

```
statuses seen: 200, 429
banner: QUERY_ERROR: Too many requests from this IP, please try again after 15 minutes.
```

The API sends `Retry-After`, but the UI ignores it, offers no countdown, no
retry, and no backoff. Manually clicking EXECUTE keeps re-firing.

### C6. Radius slider contradicts the API

Slider range is `2–50 km`; the API accepts up to `100 km` and the docs say
"Maximum: 100". Users cannot reach the documented maximum.

### C7. Favicon 404 on every page

`frontend/public/favicon.svg` exists, but `index.html` has no `<link rel="icon">`,
so the browser requests `/favicon.ico` and gets 404 — confirmed in the console
log on every page load.

### C8. Third-party CDN stylesheet at runtime

`<link rel="stylesheet" href="https://unpkg.com/leaflet@1.9.4/dist/leaflet.css">`
is in the HTML template, so it loads on all 8 pages. `leaflet` is already a local
dependency; if unpkg is slow or blocked the map renders unstyled and unusable.

## D. Design — the "AI slop" you asked about

The current UI is the default "hacker telemetry dashboard" template:

1. **Palette**: near-black navy `#080c14` canvas, `#0e1526` panels, three accent
   colours at once (blue `#2563eb`, emerald `#10b981`/`#34d399`, amber `#f59e0b`),
   plus teal `#0d9488` map markers. Four competing accents is why it reads as
   generic rather than designed.
2. **Shouting labels**: `SEARCH_PARAMETERS`, `EXECUTE /v1/stations/near`,
   `TOTAL_IN_RADIUS`, `DATA_ENGINE: HAVERSINE_SPATIAL_V1`, `INDEX_METRICS`,
   `GATEWAY: OPERATIONAL`, `CORE_DATABASE_BENCHMARKS`, `OPEN_SPEC →`,
   `RETURN_TO_HOME`, `REPO`. Monospace uppercase is supposed to signal "terminal",
   but at this density it is just noise — and it is applied to prose.
3. **Widget chrome**: every block is a `.panel-technical` box with a
   `.panel-header` strip, so the page reads as a grid of identical framed
   rectangles. Plus `box-shadow: 0 0 6px #3b82f6` glow on the map marker.
4. **Dark map by inversion**:
   `filter: invert(100%) hue-rotate(180deg) brightness(85%)` on the OSM tile pane.
   This inverts map *imagery*, so water, parks, roads and label colours are all
   wrong, and text is inverted from a raster — it never looks intentional.
5. **Three sources of truth for colour**: inline hex in JSX, CSS custom
   properties in `index.css`, and an unused `ev.*` palette in `tailwind.config.js`.
6. **Fabricated telemetry presented as fact**: "AVG_SPATIAL_LATENCY < 3.8 ms",
   "SLO Target", "Parity Source: Local Gov Directory (LGD)", "STATUS: LIVE" — none
   measured or sourced.

## E. SEO

`npm run verify:seo` reports **0 errors, 11 warnings** — the "0 SEO errors" claim
is accurate, but warnings were being ignored:

| Issue | Impact |
|---|---|
| **No `og:image` / `twitter:image` on any of the 8 pages** | `twitter:card` is `summary_large_image` with no image → blank social/link previews everywhere |
| Guide titles are **74 chars** | Truncated in search results |
| No `<link rel="icon">` (see C7) | Favicon 404; no icon in tabs or SERPs |
| WebAPI JSON-LD **copied verbatim onto all 8 pages** | `/guides/*` article pages declare themselves a `WebAPI`, and carry the WebAPI block *and* a `TechArticle` block |
| `sitemap.xml` `<lastmod>` hardcoded to `2026-10-15` | Goes stale the moment content changes |
| Missing `og:site_name`, `og:locale` | Weaker previews |
| Canonical/sitemap/robots point at a 404 host (A) | Crawlers are directed to a dead site |

## F. Basemap licensing (found while investigating D4)

- **CARTO raster basemaps now require an API key** (since 25 Sep 2026) and stamp
  an "API KEY REQUIRED" watermark on keyless requests. The URL recorded in
  `DOCS/PLAN-MAP-INTEGRATION.md` (`basemaps.cartocdn.com/dark_all`) is dead.
- **`tile.openstreetmap.org` in a public web app violates the OSMF Tile Usage
  Policy.** The policy states capacity is best-effort with no SLA and that heavy
  or inappropriate use will be blocked without notice; it explicitly says to use
  an alternative OSM-derived service if you cannot meet the requirements.
- **OpenFreeMap** is the correct fit for this project: no API key, no
  registration, no request limits, commercial use permitted, MIT-licensed, vector
  tiles from OpenStreetMap. Requires MapLibre GL (WebGL) instead of Leaflet.
